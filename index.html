A practical field guide · edition 01

Make good work together.

GitHub is where projects get a memory, a meeting place, and a way to improve safely. This guide turns the unfamiliar words into a workflow you can actually use.

Start with the basics ↓No coding background required to begin.

Think of Git as the rewindable history of your project. GitHub is the online home where that history can be shared, reviewed, and built on.

$ git status # what changed?
$ git add README.md
$ git commit -m "Explain the project"
$ git push # share it on GitHub

Change · make a draft

Edit a file, fix a typo, sketch an idea, or update a plan. Your working copy is where you can experiment before sharing.

Git is the time machine

Git tracks changes on your computer: what changed, when, and in which saved snapshots. You can compare versions and restore earlier work.

GitHub is the workshop

GitHub hosts Git repositories online and adds collaboration: reviews, discussions, issue tracking, project planning, and automation.

02 / THE MENTAL MODEL

Learn the handful of words that unlock the map.

The names feel technical at first. Each one is just a place, a copy, or an action in the story of a project.

One project, a few useful places

(repo) = project files plus their full history. It can be public or private. A is a copy hosted somewhere else, often GitHub.

Your is a complete local copy. You edit it on your device, then push commits to GitHub. To bring other people's updates down, you pull.

Keep the stable version calm

A is a parallel line of work. Make one for a feature or fix so your draft does not disrupt the stable branch (often called main).

A is a named snapshot. A joins one line of work into another.

Invite the conversation

A (PR) proposes changes from one branch to another. People can comment on the exact lines, discuss, and request improvements before merge.

Work from a copy you own

A is your GitHub-side copy of someone else's repository. Use it when you cannot push directly, such as contributing to an open-source project.

Should I create a branch or a fork?

Choose an option for a quick recommendation.

Local ↔ remote: local means on your computer; remote means hosted online. “Push” sends your committed work up. “Pull” brings remote work down. A commit alone does not upload anything.
03 / YOUR FIRST REPOSITORY

Pick your path. The destination is the same.

You can start right in the browser, use GitHub Desktop for visual controls, or use Git in a terminal. Use the tabs to choose your first trip.

No install needed

Start on GitHub.com

Create a new repository, choose a short name like weekend-recipes, add a README, and decide whether the project should be public or private. Then open the README and use the edit control to add a sentence.

  1. Create: choose New repository. Add a description and initialize with a README so the project has a welcoming front page.
  2. Change: edit README.md in the browser. Write what the project is, who it helps, and how to use it.
  3. Save: choose a clear commit message such as “Add project introduction.” Save directly to main for this tiny solo example, or create a branch to practice the review flow.
  4. Try a pull request: create a branch, edit a second line, then propose merging that branch into main. Review the diff and merge when it looks right.

Browser editing is great for quick changes, docs, and learning. For larger projects, edit locally with Desktop or your preferred tools.

Visual Git workflow

Use GitHub Desktop

Desktop puts common Git actions behind buttons: clone or create a repo, see changed files, write a commit message, publish, and open a pull request.

  1. Install GitHub Desktop from the official site and sign in to your GitHub account.
  2. Create a repository or clone one you already have. Choose a folder where you want the local copy to live.
  3. Open the project in an editor and make a small change. Desktop shows changed files and a side-by-side diff.
  4. Write a short summary (“Add setup instructions”), commit to your branch, then Publish branch or Push origin to send the commit to GitHub.
  5. Preview a pull request, describe why the change helps, and create it on GitHub for review.

Desktop is an approachable way to learn Git because it makes the changed files and history visible.

For command-line comfort

Use Git in a terminal

These commands create a local project and connect it to GitHub. Create an empty repository on GitHub first, then replace the URL below with its HTTPS address.

mkdir weekend-recipes
cd weekend-recipes
git init
echo "# Weekend Recipes" > README.md
git add README.md
git commit -m "Start recipe collection"
git branch -M main
git remote add origin https://github.com/YOUR-NAME/weekend-recipes.git
git push -u origin main

For a later change, make a branch, edit files, then stage and commit only the work you intend to save:

git switch -c docs/add-setup
git status
git add README.md
git commit -m "Add setup notes"
git push -u origin docs/add-setup

Then open a pull request on GitHub from docs/add-setup into main. git status is your friend: it tells you which branch you are on and what is still unsaved.

Never paste a password or token into a command that might be saved in shell history. Use GitHub's supported sign-in flow, Git Credential Manager, or SSH setup from the official docs.

Start here · essential

Files and README: the front door

The README.md is the project’s introduction. Markdown makes simple formatting easy: headings, lists, links, images, and code snippets. A good README answers: what is this, how do I get started, and where can I ask for help?

# Weekend Recipes

A growing collection of quick meals for busy evenings.

## Try it
- Pick a recipe
- Share a variation

GitHub can edit files in the browser, show diffs, render Markdown, and let you browse folders. Avoid uploading secrets such as API keys, passwords, private data, or credentials.

Essential

Branches and commits: work in small, named steps

Make a branch for a focused piece of work: fix/mobile-menu or docs/installation. Keep commits small enough to explain in one sentence. A good commit message says what changed and why: “Explain installation steps” beats “updates.”

Before committing, check the diff. Added lines are usually green; removed lines red. The diff is a chance to catch accidental files or changes. Push your branch when you want GitHub or teammates to see it.

Useful rhythm

Check status → inspect diff → stage intended files → commit with a clear message → push when ready.

One change per branch

Mixing unrelated fixes makes reviews harder. A focused branch gets faster, clearer feedback.

Essential for teamwork

Pull requests: a proposal with a built-in conversation

A PR compares a source branch to a target branch and displays the exact changes. It is both a review request and a place to discuss how the change should land. Open it early if feedback could steer the work; mark it as a draft when it is not ready to merge.

A useful PR description

  • Why: the problem or goal.
  • What: the key changes.
  • How checked: what you tested or reviewed.
  • Context: link a related issue with wording such as “Closes #12.”

Reviewers can comment on lines, request changes, or approve. Reply to comments and push follow-up commits to the same branch. Once required checks and reviews are satisfied, an authorized person can merge. A merge conflict means both branches changed overlapping parts; open the conflict, choose the intended combined result, and run the project’s checks again.

A pull request is not a “pull” command. It is a proposal to merge one branch into another. You can open one before the work is finished to invite early discussion.
Essential for collaboration

Issues and Discussions: talk about the work

Use an issue to track a task, bug, question, or idea that needs follow-through. A strong issue has a clear title, steps to reproduce (for a bug), expected versus actual behavior, and relevant screenshots or context. Labels, assignees, and milestones help organize the queue.

Use Discussions for open-ended questions, announcements, or ideas that benefit from conversation before becoming a task. Projects can pull issues and PRs into a shared planning view.

Optional · useful as work grows

Projects: see what is moving

GitHub Projects helps teams organize issues and pull requests in a table, board, or roadmap-style view. Fields can capture status, priority, dates, or owners. A simple board often works well: Todo → In progress → Done. Link the actual issue or PR so planning stays connected to the work.

Start with a small set of columns and fields. A board is a shared map, not a substitute for clear issue descriptions or conversations.

Optional · sharing a finished version

Releases and packages: mark a milestone

A tag names a point in history, often a version such as v1.2.0. A GitHub Release adds human-readable notes and can attach downloadable files. Tell readers what changed, what they may need to update, and any known limitations.

Packages are versioned outputs such as libraries or container images. They are useful when a project publishes software for other projects to install; many repositories never need them.

Optional · powerful tools

Actions and Pages: let the project do more

GitHub Actions runs workflows in response to events such as a push or pull request. Teams use it for automated tests, builds, and release steps. A workflow is defined in YAML under .github/workflows/. Start with a trusted template, read what permissions it requests, and avoid giving workflows broader access than they need.

GitHub Pages can publish a website from a repository, often useful for documentation, portfolios, and project pages. Check repository visibility, Pages settings, and your plan or organization policy; available options can vary.

Both are optional. Learn the repository and pull request loop first, then automate repetitive steps that are clear and safe.

05 / OPEN SOURCE

Contribute to a project you don’t own.

A fork lets you make a copy in your account. Your changes can then travel back as a pull request for maintainers to consider.

The contribution route

  1. Read the README and contribution guidelines; check existing issues or discussions first.
  2. Fork the repository to your account, then clone your fork to work locally.
  3. Create a focused branch, make a small change, and commit it clearly.
  4. Push the branch to your fork and open a pull request to the original repository.
  5. Explain the benefit, link the relevant issue, respond kindly to feedback, and update the PR if needed.

Good open-source manners

Maintainers are people donating time. Be specific, patient, and respectful. Follow the project’s conventions and code of conduct. A documentation typo fix is a perfectly good first contribution.

If a project says it is not accepting contributions, respect that. If your PR is not accepted, the review can still teach you how the project works.

06 / ACCESS & SAFETY

Share deliberately. Protect the keys.

The easiest security problem to prevent is a secret that never gets committed. Decide who can see and change a project before you invite people in.

Public or private?

Public: anyone can view it; contributors still need permission to push. Choose public for open collaboration or a portfolio when the contents are safe to share.

Private: access is limited to people you invite (and organization rules). Choose private for work that should not be visible publicly. Remember that access settings and feature availability can depend on an organization or plan.

Permission basics

Give collaborators only the access they need. In an organization, teams can make membership and repository permissions easier to manage. Review access when people change roles or leave a project.

Use branch protection and required reviews/checks when a team needs safeguards around its important branch.

Will everyone who needs access be comfortable seeing this repository?

Choose an option for a quick recommendation.

Secure your account

Turn on two-factor authentication or a passkey where available. Keep recovery methods current. Review authorized apps and SSH keys; remove ones you no longer recognize or use.

Keep secrets out of Git

Never commit passwords, private keys, API tokens, or customer data. Put local secrets in environment variables or a gitignored local config file. For automation, use repository or environment secrets with narrow access.

Choose a license

If you want others to reuse public code, include a license that states the permissions and conditions. Public visibility alone does not grant an open-source license.

Think before running workflows

Review third-party Actions and workflow permissions. A workflow can execute code and access credentials, so use maintained sources and grant the minimum required scope.

If a secret was committed: revoke or rotate it immediately. Deleting it in a later commit does not erase it from repository history. Follow GitHub’s official sensitive-data removal guidance and notify the right security contact.

08 / WHEN THE PATH GETS BUMPY

Quick fixes for common “wait, what?” moments.

Pause before forcing anything. Git’s history is useful; most tangles are easier to unwind when you know your current branch and have a backup.

“I edited the wrong branch.”

Check git status and the branch name. If you have not committed, switch carefully and move or stash the changes. In Desktop, confirm the current branch before committing. Avoid deleting anything until the work is safe.

“There’s a merge conflict.”

Git could not combine overlapping edits automatically. Open each conflicted file, compare both versions, edit the final intended text, remove conflict markers, then test and commit the resolution.

“Push was rejected.”

The remote may have commits you do not have, or permissions may be missing. Fetch/pull and integrate the remote updates, then push again. Read the error carefully; do not force-push a shared branch to silence it.

“I got feedback on my PR.”

Reply in the thread, make the requested change on the same branch, commit and push. The PR updates automatically. Ask a clarifying question if the request is unclear.

“I committed a token.”

Revoke or rotate it now. Removing the line in another commit does not make the old credential safe. Then remove it from history if needed and check logs or access for unexpected use.

“I can’t find the right action.”

Look for current guidance in GitHub Docs. The interface and labels can change; menu locations and available features can differ for organizations and plans.

10 / POCKET GLOSSARY

Words to keep nearby.

Open a term for the short version. Use the search at the top to find a concept elsewhere in the guide.

Repository (repo)

A project’s files plus their full version history.

Branch

A separate line of work that can evolve without changing another branch.

Commit

A saved snapshot of selected changes, with a message about what changed.

Clone

A complete local copy of a repository, including its history.

Remote

A repository copy hosted elsewhere, commonly on GitHub.

Push / Pull

Push sends local commits to a remote. Pull brings remote commits into your local branch.

Fork

Your own GitHub-side copy of another person’s repository.

Pull request (PR)

A proposal to merge changes from one branch into another, with a place to review and discuss them.

Merge

Combines the changes from one branch into another.

Issue

A trackable task, bug, question, or idea associated with a repository.

Diff

A view of what changed between versions: added lines and removed lines.

Upstream

The original project a fork came from; often the destination for a contribution.
